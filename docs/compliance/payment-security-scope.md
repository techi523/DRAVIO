# DRAVIO — Payment Security Scope Assessment

Engineering record of the payment surface. Statuses: `PASS` / `PARTIAL` / `FAIL` /
`NOT APPLICABLE` / `UNKNOWN` / `LEGAL REVIEW REQUIRED` / `BLOCKED`.

Scope question answered by code, not brochure: **does cardholder data ever enter, transit,
or store on DRAVIO infrastructure?**

---

## 1. Card data (Stripe) — scope determination

### 1.1 What the code does

- `payment/providers/stripe.provider.ts`: `createPaymentIntent` calls
  `stripe.paymentIntents.create({ amount (integer cents), currency, metadata,
  automatic_payment_methods })` and returns `provider_ref` (PaymentIntent id),
  `client_secret`, and a `checkoutUrl`.
- Checkout happens on an **external hosted page** (`STRIPE_CHECKOUT_BASE_URL` default
  `https://checkout.dravio.com`) to which the buyer is redirected/opened
  (`apps/buyer-web/src/app/wallet/page.tsx` does `window.open(result.checkout_url)`).
- DRAVIO receives only the PaymentIntent id and webhook events. **Card number, CVV, and
  full PAN are never submitted to, generated by, or stored on any DRAVIO server.**

### 1.2 Conclusion

- DRAVIO's own environment is **not itself a cardholder-data environment** for card
  acquisition or storage: the data path (card capture) is delegated to a PCI DSS
  (Stripe) validated processor via hosted checkout.
- This is an **engineering conclusion about the code path**, not a PCI DSS attestation
  and not a SAQ-level determination. Which PCI SAQ (if any) applies to DRAVIO depends on
  the merchant-of-record arrangement, the PSP agreements, and the surviving card-message
  flows (e.g. Stripe dashboard/portal access, metadata, reconciliation copies).
  Status: `LEGAL REVIEW REQUIRED` — `SAQ guidance must be confirmed by the acquiring/PSP
  contract and a qualified security/QA consultant`, and is asserted nowhere here.
- Residual risk that remains DRAVIO's regardless: webhook signature verification
  (`verifyWebhookSignature`, `STRIPE_WEBHOOK_SECRET`) is mandatory and wired at
  `POST /v1/payments/webhook`; payment idempotency (idempotency_key + CAS `WHERE status =
  'PENDING'`); ownership-scoped status reads.

### 1.3 Conveyed metadata note

DRAVIO does send `metadata { transaction_id, user_id, session_id, phone_number }` to
Stripe at intent creation. This is personal data (see cross-border-data-flow.md §2.2) but
**not** PAN/CVV.

## 2. M-Pesa STK push (PTA / Safaricom) — scope

- `mpesa.provider.ts`: STK push carries only the normalized phone number (`254…`) and the
  amount; the buyer enters the PIN on their **own phone** in the Safaricom flow — no PIN
  and no card data touch DRAVIO.
- Callback (`POST /v1/payments/mpesa/callback`) parses `CheckoutRequestID`,
  `MerchantRequestID`, `ResultCode`, `Amount`, `MpesaReceiptNumber`, `TransactionDate`,
  `PhoneNumber`.
- **Callback integrity**: there is no cryptographic signature on M-Pesa callbacks; the
  implementation protects through (a) secret `MPESA_CALLBACK_URL`, (b) DB lookup by
  `CheckoutRequestID` (`paymentRepository.findByRef`), (c) amount reconciliation.
  Status: `PARTIAL` (sound reconciliation, but callback-authenticity depends on URL
  secrecy + identifier matching; Safaricom offers no signature to verify).
- **Amount reconciliation**: `expectedKes = round(amount_usd × USD_TO_KES_RATE)`;
  tolerance **5 KES**; mismatch → `failByRef(... 'AMOUNT_MISMATCH')`
  (`payment.service.ts`). Replays are state-machine guarded (only `PENDING` transitions).
- **Production-readiness gap**: `BASE_URL` falls back to `sandbox.safaricom.co.ke`
  (`mpesa.provider.ts:3-6`) and `MPESA_ENV` defaults to `'sandbox'` (`config/env.ts`).
  A production instance must explicitly set `MPESA_ENV=production`; otherwise callbacks
  would never match a deployed shortcode and money movement silently degrades.
  Status: `FAIL` (as a production-readiness control until the env is forced/documented).

## 3. Layering with the transaction state machine

### 3.1 States (transaction-machine.ts)

`PENDING → AUTHORIZED → PAID → FULFILLED`; failure/cancellation path `FAILED`, `CANCELLED`;
post-paid lifecycle `DISPUTED`, `PARTIALLY_REFUNDED`, `REFUNDED`, `REVERSED`.
`TERMINAL_STATES = { FAILED, REFUNDED, REVERSED }`.

Transition guard rules:

- Buyer (owner) may initiate `DISPUTED` (requires `reason`).
- `REFUND`/`PARTIALLY_REFUNDED`/`REVERSED`/`CANCELLED` are restricted to
  `BILLING_ADMIN`/`ADMIN` and require a reason.
- `SYSTEM_ROLE` drives automated `PENDING→AUTHORIZED→PAID→FULFILLED`.
- Every applied transition is persisted CAS-guarded into
  `compliance.transaction_events` and emitted to `dm.audit.log` (REDACTED).

### 3.2 Wallet / escrow semantics

- Pre-funded wallets: `billing.wallets` (`balance_usd`, `escrow_usd`, CHECK `>= 0`).
- `lockEscrow` reserves funds; `commitSessionCost` settles usage; `directDeduct` for
  metered debits; all reject overdraw (`INSUFFICIENT_FUNDS` / `Financial Overdraw
  Detected or Insufficient Funds to Commit`).
- Every verified top-up credits the wallet plus an **immutable** `billing.ledger_entries`
  row (`wallet_credit`, COMPLETED) in the same DB transaction
  (`payment.repository.completeAndCredit`).

### 3.3 Payouts — BLOCKED

- `POST /v1/billing/withdraw` (SELLER-gated via `is_seller`): atomically deducts wallet
  balance and inserts `payments.payouts (..., status 'PENDING')`. **It does not perform any
  disbursement.** There is no Stripe Connect orchestration, no B2C/P2P M-Pesa call wired to
  a route, and `stripeProvider.createPayout` is defined but unused by any route in this
  repo.
- The response text "Funds arrive within 1-3 business days" is **not backed by any
  implementation**. Withdrawn funds are deducted from the seller's wallet and parked in a
  `PENDING` payout row indefinitely.
- Status: `BLOCKED` / `PROVIDER CAPABILITY REQUIRED`. This is a legal and financial
  integrity exposure (seller obligations + consumer-protection misrepresentation) until a
  real disbursement mechanism (e.g. Stripe Connect or Safaricom B2C) is implemented and
  tested. See §4.

## 4. Payment security control status

| Control | Status | Evidence |
|---|---|---|
| Card data never enters DRAVIO surface | `PASS` | Hosted checkout; no PAN/CVV field, store, or message in repo |
| Stripe webhook signature verification | `PASS` | `STRIPE_WEBHOOK_SECRET` + `constructEvent` on raw-buffer route |
| Payment idempotency + replay-safety | `PASS` | `idempotency_key` (unique), CAS `WHERE status='PENDING'` |
| Ownership-scoped transaction reads | `PASS` | `findOwnedById` on status/history |
| M-Pesa reconciliation (5 KES tolerance) | `PASS` | `payment.service.ts` |
| M-Pesa callback authenticity | `PARTIAL` | No signature; URL-secrecy + ref lookup + amount check |
| M-Pesa production endpoint forcing | `FAIL` | Sandbox fallback default (`mpesa.provider.ts:3-6`, `env.ts`) |
| Payout / disbursement | `BLOCKED` | Only writes PENDING row; no disbursement path |
| PCI SAQ determination | `LEGAL REVIEW REQUIRED` | Depends on merchant-of-record/PSP contractual structure |
| Consumer-facing truthful payout/tariff messaging | `FAIL`/`LEGAL REVIEW REQUIRED` | "1-3 business days" claim without capability |

No certification, badge, or "PCI compliant" claim appears in this document or should be
made about DRAVIO from this assessment.
